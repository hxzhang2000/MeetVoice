## 1. 背景与目标

### 1.1 需求原文

> 实时读取电脑的输入和输出内容，实时记录会议录音，并实时将音频转换为文字，保存到本地 md 文件中。

拆解为三条核心能力：

1. **双路音频捕获**：同时抓取系统输出音频（会议软件中对方的声音）与麦克风输入（本地发言）。
2. **会议录音留存**：将原始音频落盘存档，便于复核与重转写。
3. **实时转写落盘**：将音频流转换为带说话人、时间戳的文字，实时追加写入本地 `.md` 文件。

### 1.2 设计目标

| 目标 | 说明 |
|---|---|
| **中文优先** | 会议内容以中文为主（含中英夹杂术语）；选型与默认配置面向中文准确率优化 |
| 全本地运行 | 不上传云端，保障隐私与离线可用 |
| 结构化输出 | 转写结果含 **说话人 / 时间戳 / 内容**，直接可用于会议纪要 |
| **多说话人自动分离** | 由 ASR 模型**自动识别**说话人（无需人工标注/声纹录入）；主路径 VibeVoice-ASR 与 CPU 兜底 FunASR 均原生联合产出说话人标签（详见 [§7.5](#75-说话人分离质量)） |
| 多语言兼容 | 中文为主，兼顾英文及 50+ 语种（VibeVoice-ASR 原生中英 code-switch） |
| 低门槛部署 | 有 GPU 走 7B 高精度路径；无 GPU 走中文优化轻量模型，**不走 VibeASR.cpp**（中文退化过大，见 §4.2） |
| 可中断/可恢复 | 长会议中断不丢数据，支持续录续写 |
| 会议可管理 | 每次会议为独立单元，可在桌面壳中**查看历史会议**、**回放录音+转写**、并**一键删除该会议的全部记录**（见 [§6.8](#68-会议管理)） |

> **语言定位说明**：本方案所有默认值、模型选择、风险权衡均以"中文会议"为第一优先。中文场景下 VibeVoice-ASR-7B（GPU）是准确率最优解；CPU 兜底改用中文专用模型（FunASR / SenseVoice），**不采用 VibeASR.cpp**--后者在 AISHELL4 上 WER 27.45，比 7B 退化 7.6 个百分点，且劣于 FunASR（20.41）。详见 [§4.2](#42-三条推理路径按部署形态分) 与 [§7.6](#76-中文场景的模型选择)。

### 1.3 非目标（Non-Goals）

- 不做实时字幕悬浮窗（可作为后续迭代）。
- 不做云端同步与多人协作。
- 不做 TTS 语音合成（VibeVoice 仓库虽含 TTS 能力，但不在本需求范围内）；语音对话助手（ASR+LLM+TTS 闭环）列为未来演进方向，详见 [§13](#13-未来演进方向语音对话助手)。

## 2. 需求分析

### 2.1 "实时"的歧义澄清

"实时"在会议记录场景有三种不同语义，实现成本差异极大：

| 语义 | 延迟 | 实现难度 | 适用场景 |
|---|---|---|---|
| **A. 流式转写**（字随音出） | < 1 秒 | 高 | 字幕、同声传译辅助 |
| **B. 准实时滚动**（按段落出） | 10–60 秒 | 中 | 会议中随手看纪要 |
| **C. 会后即得**（结束就出） | 会议结束几秒到几分钟 | 低 | 会后归档纪要 |

VibeVoice-ASR 的设计是 **60 分钟单次批处理**，天然适合 **B + C**：
- B（准实时滚动）：每攒满 30–60 秒音频送一次 ASR，追加到 MD。
- C（会后终稿）：会议结束后用完整音频再跑一次，产出全局一致说话人编号的干净终稿。

**本方案推荐 B+C 混合**：滚动出稿保证"会议中可读"，终稿出片保证"会后可用"。若用户确需 A（亚秒级字幕），需引入轻量流式 ASR（如 faster-whisper / paraformer-streaming）做实时预览，VibeVoice-ASR 仅做终稿——见 [§7.4](#74-实时字幕可选路径-a)。

### 2.2 输入输出契约

```
输入：
  - 系统输出音频流（WASAPI Loopback, 48kHz 采集为 float32）
  - 麦克风输入流（默认采集设备, 48kHz 采集为 float32）
  - 可选：热词表、已知说话人名（context_info）

输出（同一会议的所有文件共享会议 id = 开始时间戳 YYYYMMDD_HHMMSS）：
  - 会议记录：recordings/YYYYMMDD_HHMMSS.json（会议元数据 + 全部关联产物路径 + 状态，见 §6.2 / §6.8）
  - 录音归档：recordings/YYYYMMDD_HHMMSS_sys.wav / _mic.wav
  - 实时纪要：notes/YYYYMMDD_HHMMSS_live.md（滚动追加）
  - 终稿纪要：notes/YYYYMMDD_HHMMSS_final.md（会后重排，含多说话人自动编号）
  - 会议总结：notes/YYYYMMDD_HHMMSS_summary.md（LLM 会后生成，可配置，见 §6.7）
  - 运行日志：logs/YYYYMMDD_HHMMSS.log
```

## 4. 技术基线（已核验事实）

> 以下结论均来自 `VibeVoice-main.zip` 源码与官方 README，可追溯。

### 4.1 VibeVoice-ASR 模型能力（确认属实）

- **长音频单次处理**：单次接受最长 **60 分钟**连续音频（64K token 上限内），无需切片。源码 `demo/vibevoice_asr_inference_from_file.py` 的 `--max_duration` 默认 3600 秒。
- **结构化输出**：联合产出 **Who（说话人）/ When（时间戳）/ What（内容）**。`VibeVoiceASRProcessor.post_process_transcription()` 返回 `[{start_time, end_time, speaker_id, text}, ...]`。
- **多说话人自动分离（diarization）**：模型**原生联合**完成 ASR + 说话人分离 + 时间戳对齐，输出即带 `speaker_id`，**无需人工标注/声纹录入、无需指定人数**（自动聚类）。官方模型卡与 Azure 目录均确认其"jointly performs ASR, diarization, and timestamping"，60min 单 pass 内维持全局说话人一致性（DER 见 §7.5）。CPU 兜底 FunASR 同样一次调用出说话人（VAD+ASR+标点+原生 diarization，自动聚类，2026-05 起无需 CAM++）。
- **多语言**：50+ 语种原生支持，无需显式指定语言，支持句内中英 code-switch。
- **热词定制**：通过 `context_info` 参数传入人名、术语、背景信息，提升专有词准确率。
- **模型规格**：`VibeVoice-ASR-7B`（7B 参数，HF: `microsoft/VibeVoice-ASR`），基座为 Qwen2.5-7B。

### 4.2 三条推理路径（按部署形态分）

| 路径 | 模型 | 硬件 | 来源 | 适用 |
|---|---|---|---|---|
| **transformers 直跑** | `microsoft/VibeVoice-ASR-HF` | GPU（CUDA/bf16/flash-attn2）或 CPU（fp32/sdpa，慢） | `pyproject.toml` + Gradio demo | 开发调试、灵活定制 |
| **vLLM 服务化** | `microsoft/VibeVoice-ASR` | NVIDIA GPU | `vllm_plugin/` + `docs/vibevoice-vllm-asr.md` | 多并发生产部署，OpenAI 兼容 API + 流式输出 |
| **VibeASR.cpp**（独立仓库） | `microsoft/VibeVoice-ASR-BitNet` | **纯 CPU**，3+ 线程 RTF<1 | https://github.com/microsoft/VibeASR.cpp | 无 GPU 的笔记本/办公机 |

> 注：`microsoft/VibeVoice-ASR` 为基座权重，`microsoft/VibeVoice-ASR-HF` 为已集成进 Transformers 的调用版本（`trust_remote_code=True`）；二者指向同一模型族，配置中的 `model_path` 用基座 id 即可。

**VibeASR.cpp 已核验事实**（来自官方 GitHub README，2026-08-12 拉取）：

- **定位**：VibeVoice-ASR-BitNet 的官方 CPU 推理运行时，基于 ggml 框架，SIMD 核子 + 算子融合。
- **量化方案**：异构量化--VAE 用 I8_S，LM 用 I2_S（BitNet），LM 词嵌入用 Q6_K。
- **模型替换**：将原 Qwen2.5-7B LM 换成 Qwen2.5-1.5B，WER 绝对增加 1–4%，换取体积与速度。
- **体积**：4.62 GB → **1.58 GB**（VAE 0.65 GB + LM 0.92 GB，2.9× 压缩）。
- **速度**：**1.6–2.3× faster than Whisper.cpp**（官方 benchmark 实证）。
- **RTF 实测**（README benchmark 表）：

| 平台 | 1T | 2T | 3T | 4T | 6T | 8T |
|---|---|---|---|---|---|---|
| AMD EPYC 7V13 (AVX2) | 1.98 | 1.08 | 0.77 | 0.63 | 0.49 | **0.42** |
| Apple M4 (NEON) | 1.18 | 0.68 | 0.52 | 0.43 | 0.48 | **0.42** |
| Intel i7-13700 (AVX2, Win11) | 1.55 | 0.97 | 0.78 | 0.71 | 0.67 | 0.69 |

  > RTF < 1 即实时；8 线程下三方平台均达标。**0.42 是 RTF，不是秒。**
- **精度**：MLC-EN WER 8.25（7B 原版 7.82，退化 0.43）；AISHELL4 WER 27.45（7B 19.83，退化较大--中文长会议场景需评估）。
- **依赖**：Python ≥ 3.9，CMake ≥ 3.14，GCC/Clang（C++11），约 2 GB 磁盘。
- **接口形态**（关键）：
  - **CLI**：`./build/bin/asr_infer --vae-model <gguf> --lm-model <gguf> --audio input.wav -t 4`
  - **Gradio demo**：`python demo/gradio_asr_demo.py --port 7860`
  - **无 HTTP/WebSocket server**、**无 Python 绑定**、**无流式音频输入**--只能按文件输入做批处理。
- **Windows 限制**（重要）：
  - **MSVC 不被支持**，`src/CMakeLists.txt` 会主动拒绝。
  - 必须用 **MinGW-w64**（推荐 [WinLibs](https://winlibs.com/)），用 `MinGW Makefiles` 生成器。
  - **`setup_env.py` 在 Windows 上不可用**（其 clang 探测假设 POSIX shell），必须走手动 cmake 构建。
  - 运行时需把 MinGW `bin` 目录留在 `PATH` 中，否则找不到 DLL。

### 4.3 关键 API（源码实证）

来自 `demo/vibevoice_asr_inference_from_file.py` 与 `demo/vibevoice_asr_gradio_demo.py`：

```python
from vibevoice.modular.modeling_vibevoice_asr import VibeVoiceASRForConditionalGeneration
from vibevoice.processor.vibevoice_asr_processor import VibeVoiceASRProcessor

# 1. 加载（device 支持 cuda/mps/xpu/cpu/auto）
processor = VibeVoiceASRProcessor.from_pretrained(
    model_path, language_model_pretrained_name="Qwen/Qwen2.5-7B"
)
model = VibeVoiceASRForConditionalGeneration.from_pretrained(
    model_path, dtype=torch.bfloat16, attn_implementation="flash_attention_2",
    trust_remote_code=True,
).to("cuda")

# 2. 转写（支持文件路径或 (array, sr) 元组）
inputs = processor(audio=audio_path_or_array, sampling_rate=None,
                   return_tensors="pt", add_generation_prompt=True,
                   context_info="张三\n李四\nVibeVoice")  # 热词
output_ids = model.generate(**inputs, max_new_tokens=32768, do_sample=False)
text = processor.decode(output_ids[0, inputs["input_ids"].shape[1]:], skip_special_tokens=True)

# 3. 解析结构化分段
segments = processor.post_process_transcription(text)
# => [{"start_time": 0.0, "end_time": 2.3, "speaker_id": 0, "text": "..."}, ...]
```

**依赖**（`pyproject.toml`）：Python ≥ 3.10，`torch`、`transformers>=4.51.3,<5.0.0`、`accelerate`、`librosa`、`gradio`、`fastapi`、`uvicorn[standard]`、`pydub`、`av`、`aiortc`。

> 实施前请以 `third_party/VibeVoice/pyproject.toml` 的**实际约束**为准复核 `transformers` 版本上界——社区已有 transformers 5.3.0+ 可正常加载该模型的反馈，本文撰写时的 `<5.0.0` 可能已过时，需随官方版本迭代更新。

README 明确声明：*"We do not recommend using VibeVoice in commercial or real-world applications without further testing and development. This model is intended for research and development purposes only."* 因此本方案定位为**个人/内部工具**，不对外提供在线服务。

### 4.5 模型管理规范（选型 · 存放 · 配置）

> 本节在 §4.1–§4.4 已核验的模型事实基础上，给出**可落地的统一管理规则**：选哪个、放哪、怎么配。所有后端适配器（§6.3）均按本节的 `backend` 值与配置字段实现；运行产物（`recordings/` `notes/` 等）的存放不在此节，见 §6.6 `[paths]`。

#### 4.5.1 模型选型规则

选型由两层决定：**自动推荐**（启动自检 / 首次向导）与**手动覆盖**（`[asr].backend` 配置优先于自动推荐）。

**决策维度**：① 硬件（是否有 GPU、显存大小）② 语言（中文会议为主 / 纯英文）③ 场景（长会议高精度 / 实时流式预览 / 无 GPU 办公机）④ 部署形态（本地直跑 / 多并发服务化）。

**选型矩阵**（与 §5 选型表、§7.6 决策树一致）：

| 条件 | 选型 | `backend` 值 | 关键说明 |
|---|---|---|---|
| 有 GPU（≥8GB 显存） | VibeVoice-ASR-7B（transformers, bf16 + flash-attn2） | `vibevoice_local` | 默认主引擎；中文 AISHELL4 WER 19.83 最优 |
| 有 GPU 且想更小/全开源 | MOSS-Transcribe-Diarize 0.9B（transformers, trust_remote_code） | `moss_local` | 0.9B、Apache-2.0；端到端 ASR+diarization+时间戳，90min 单 pass；AISHELL-4 CER 14.84 优于 VibeVoice（同口径 CER 21.40；VibeVoice 另报 WER 19.83）；重叠/打断处理更稳（见 [§6.3](#63-asr-适配器)） |
| 有 GPU 且需多并发服务化 | VibeVoice-ASR via vLLM | `vibeasr_vllm` | OpenAI 兼容 HTTP + 流式 token 出字 |
| 无 GPU + 中文会议 | FunASR Paraformer-large（CPU） | `funasr_local` | 中文 WER 20.41；**已原生支持 diarization（2026-05 起），无需 CAM++**；GGUF 运行时可纯 CPU 单文件零 Python 跑（2026-06） |
| 无 GPU + 中文且追求速度 | SenseVoice-Small（CPU） | `funasr_local`（`funasr_model="sensevoice-small"`） | 体积更小、更快；GGUF q8 约 250MB |
| 无 GPU + 纯英文 | VibeASR.cpp BitNet（CPU） | `vibeasr_cpp` | 英文 RTF<1；**中文会议不用**（WER 27.45） |
| 极致精度可选（有 GPU+大显存） | FireRedASR2S LLM 版（8.3B） | `fireredasr_local` | 普通话 CER 2.89（AISHELL-1 仅 0.57%），精度 SOTA；但需 32GB+ 显存、AED 版单条限 60s |
| 多语言/效率可选 | Qwen3-ASR 1.7B（52 语言） | `qwen3asr_local` | 0.6B 版 10 秒处理 5 小时音频；diarization 能力待确认 |
| 实时流式预览（v2） | FunASR streaming / SherpaONNX | `funasr_streaming` | 仅预览，不入库 |

**自动推荐伪逻辑**（onboarding 与每次启动自检共用）：

```python
def recommend_backend(gpu_ok, vram_gb, lang, need_concurrency):
    if need_concurrency and gpu_ok:
        return "vibeasr_vllm"
    if gpu_ok and vram_gb >= 8:
        return "vibevoice_local"      # 默认；若用户偏好更小/全开源，设置可选 moss_local
    if gpu_ok and vram_gb >= 4:        # 低显存：优先 moss_local（0.9B 对显存更友好），必要时 vibevoice_local + device_map="auto" 分片
        return "moss_local"
    if lang == "zh":
        return "funasr_local"
    return "vibeasr_cpp"               # 纯英文无 GPU 兜底
```

**模型规模变体**：VibeVoice-ASR 的 LM 可由 Qwen2.5-7B 换为 Qwen2.5-1.5B（§4.2），WER 绝对增加 1–4%，换取体积与速度；显存 4–8GB 且不愿分片时可选。FunASR 在 Paraformer-large 与 SenseVoice-Small 间按「精度 vs 速度」权衡。

**覆盖规则**：`[asr].backend` 显式配置时直接使用该值，跳过自动推荐；UI 设置页改动此类项需重启（热更新边界见 §4.5.3）。

## 6. 模块设计

### 6.1 音频捕获模块（`meetvoice/audio/`）

**职责**：双路同步采集系统输出与麦克风，统一重采样到 24kHz 单声道浮点（VibeVoice 期望采样率），写入环形缓冲并提供窗口切片。

**核心实现**（Windows WASAPI Loopback，无需虚拟声卡）：

```python
# meetvoice/audio/capture.py（示意）
import threading
import time
import soundcard as sc
import numpy as np
import librosa  # 或 scipy.signal.resample_poly

TARGET_RATE = 24000   # VibeVoice / FunASR 期望采样率
NATIVE_RATE = 48000   # WASAPI loopback 原生速率；python-soundcard 不做重采样，
                      # 必须以设备原生速率采集后再手动转采样，否则多数机器会失败或速率错乱

class DualStreamCapture:
    def __init__(self):
        self.mic = sc.default_microphone()
        # wasapi loopback: 抓取默认扬声器的回放流（用设备 id，而非显示名）
        self.speaker = sc.default_speaker()
        self._stop = False
        self._paused = threading.Event()   # 清空=录制中，置位=暂停

    def pause(self):
        self._paused.set()

    def resume(self):
        self._paused.clear()

    @staticmethod
    def _to_mono(x: np.ndarray) -> np.ndarray:
        return x.mean(axis=1) if x.ndim > 1 else x

    @staticmethod
    def _resample(x: np.ndarray) -> np.ndarray:
        return librosa.resample(x.astype(np.float32),
                                orig_sr=NATIVE_RATE, target_sr=TARGET_RATE)

    def stream_chunks(self, chunk_seconds: float = 0.5):
        """生成 (sys_audio, mic_audio) 二元组，每段 chunk_seconds 长（已重采样到 TARGET_RATE）。"""
        with sc.get_microphone(id=self.speaker.id,
                               include_loopback=True).recorder(
                               samplerate=NATIVE_RATE) as sys_rec, \
             self.mic.recorder(samplerate=NATIVE_RATE) as mic_rec:
            chunk = int(NATIVE_RATE * chunk_seconds)
            while not self._stop:
                if self._paused.is_set():
                    time.sleep(0.1)
                    continue
                sys_data = self._resample(self._to_mono(sys_rec.record(numframes=chunk)))
                mic_data = self._resample(self._to_mono(mic_rec.record(numframes=chunk)))
                yield sys_data, mic_data
```

**兜底**：若 `soundcard` 在某些声卡上 loopback 失败，回退到 `PyAudioWPatch` 的 `as_loopback=True`；再不行才建议 VB-CABLE。

**设计要点**：
- **双路分轨仅用于分别存档与可选路由，不是说话人分离**。说话人分离由 ASR 模型的 diarization 在**混合单声道**（sys+mic 合并，见 §6.5 `sys_chunk + mic_chunk`）上自动完成；原始双路 wav 仍分轨保存便于复核。
- **已知限制（声学）**：若同一房间多人共用一支麦克风（本机 mic 物理混成一路），模型无法区分该麦克风下的不同人——他们会在转写中坍缩为同一说话人。可接受的解法：远端参会者走系统声音（各自独立声源），本地多人尽量各用独立麦克风（未来可扩展）；v1 接受"模型 diarization 在混合音频上的分离上限"，并在 UI 允许人工按段重指派说话人（见 §6.8）。
- 环形缓冲保留最近 120 秒，防止 ASR 队列阻塞时丢数据。
- 静音检测（能量阈值）用于窗口切分，避免无意义段落。

### 6.2 录音归档模块（`meetvoice/recorder/`）

**职责**：将原始双路音频同步落盘为 WAV，并写入「会议记录」JSON，供复核、终稿重转写与会议管理（§6.8）使用。

- 文件名：`recordings/YYYYMMDD_HHMMSS_{sys,mic}.wav`（16bit PCM，24kHz）。

### 6.3 ASR 引擎适配器（`meetvoice/asr/`）

**职责**：屏蔽三类后端差异，对外统一 `transcribe(audio: np.ndarray, sr: int) -> List[Segment]` 接口。

```python
# meetvoice/asr/base.py
from dataclasses import dataclass
from typing import Protocol, List

@dataclass
class Segment:
    start_time: float
    end_time: float
    speaker_id: int
    text: str

class ASRBackend(Protocol):
    def transcribe(self, audio: np.ndarray, sr: int,
                   hotwords: str | None = None) -> List[Segment]: ...
    def warmup(self) -> None: ...
```

**五个候选实现**（按中文场景优先级排序；FireRedASR2S / Qwen3-ASR 适配器在后续里程碑实现，不阻塞 v1 主线）：

| 文件 | 后端 | 角色 | 说明 |
|---|---|---|---|
| `vibevoice_local.py` | transformers + VibeVoice-ASR-7B | **默认主引擎** | GPU 走 bf16+flash-attn2；中文 AISHELL4 WER 19.83 最优；含 diarization+时间戳+热词 |
| `moss_local.py` | transformers + MOSS-Transcribe-Diarize 0.9B | **GPU 高性价比候选** | 0.9B、Apache-2.0；端到端 ASR+diarization+时间戳，单 pass 90min；AISHELL-4 CER 14.84 优于 VibeVoice-ASR（同口径 CER 21.40；VibeVoice-ASR 另报 WER 19.83）；重叠/打断更稳；需 `trust_remote_code=True` |
| `funasr_local.py` | FunASR Paraformer-large | **CPU 兜底（中文）** | 无 GPU 时的默认兜底；中文 WER 20.41，优于 VibeASR.cpp；支持热词；**一次 `generate()` 调用即联合完成 VAD+ASR+标点+原生 diarization，自动聚类说话人、无需指定人数**（2026-05 起）；GGUF 运行时可纯 CPU 单文件零 Python 跑（见 [§7.5](#75-说话人分离质量)） |
| `vibevoice_vllm.py` | vLLM HTTP（OpenAI 兼容） | 多并发服务化 | 调 `POST /v1/chat/completions`，audio 以文件路径或 base64 传入；支持流式 token 出字 |
| `vibeasr_cpp.py` | VibeASR.cpp CLI 子进程 | **仅英文/轻量场景** | 中文 WER 27.45 退化过大，中文会议不用；调用 `./build/bin/asr_infer --audio <wav>` |

> 另 **FireRedASR2S**（`fireredasr_local`）、**Qwen3-ASR**（`qwen3asr_local`）作为可选扩展后端，按 [§4.5.1](#451-模型选型规则) 矩阵纳入（极致精度 / 多语言能力），对应适配器在后续里程碑实现，不阻塞 v1 主线。

**`vibeasr_cpp.py` 适配要点**（基于已核验的 CLI API）：

```python
# meetvoice/asr/vibeasr_cpp.py（示意）
import subprocess, json, tempfile, soundfile as sf
from pathlib import Path

class VibeAsrCppBackend:
    def __init__(self, cfg):
        self.bin = cfg.asr_cpp_bin            # build/bin/asr_infer(.exe)
        self.vae = cfg.asr_cpp_vae            # vibeasr-vae-encoder-i8_s.gguf
        self.lm  = cfg.asr_cpp_lm             # vibeasr-lm-i2_s-embed-q6_k.gguf
        self.threads = cfg.asr_cpp_threads    # 推荐 4~8

    def transcribe(self, audio, sr, hotwords=None) -> list[Segment]:
        # VibeASR.cpp 只接受文件输入，写临时 wav
        with tempfile.NamedTemporaryFile(suffix=".wav", delete=False) as f:
            sf.write(f.name, audio, sr, subtype="PCM_16")
            tmp = f.name
        try:
            proc = subprocess.run(
                [self.bin, "--vae-model", self.vae, "--lm-model", self.lm,
                 "--audio", tmp, "-t", str(self.threads)],
                capture_output=True, text=True, check=True, timeout=300,
            )
            return self._parse(proc.stdout)   # 解析 CLI 输出为 Segment 列表
        finally:
            Path(tmp).unlink(missing_ok=True)
```

**约束**：
- VibeASR.cpp 无流式输入，必须"写临时 wav -> 调 CLI -> 解析"，每段有进程启动开销（约 0.5–1 秒）。滚动窗口不宜过短（建议 ≥ 30 秒）。
- VibeASR.cpp 输出格式需在 M9 阶段实测确认（README 未明确 stdout JSON 结构，可能需读 Gradio demo 源码 `demo/gradio_asr_demo.py` 确认解析方式）。
- 不支持热词 `context_info`（BitNet 路径暂未提供此能力，以实测为准）。

### 6.4 Markdown 写入模块（`meetvoice/writer/`）

**职责**：把 `Segment` 列表格式化为 Markdown，实时追加 + 会后重排。

**live.md 滚动模板**：

```markdown
# 会议纪要 · 2026-08-12 14:30 开始

> 滚动出稿，可能存在重复或说话人编号跳跃；会后请参考 final.md

## 说话人 0
- **14:30:12** 今天我们先过一下 VibeVoice 的接入方案。
- **14:30:31** 重点是音频捕获和 ASR 调度两块。

## 说话人 1
- **14:30:48** 那系统声音和麦克风要分开存吗？
```

**final.md 终稿模板**（会后一次性产出，说话人全局连续编号）：

```markdown
# 会议纪要 · 2026-08-12 14:30–15:42

**与会**：说话人 0、说话人 1
**时长**：72 分 14 秒
**热词**：VibeVoice、ASR、WASAPI

---

## [00:00]–[02:18]  说话人 0
今天我们先过一下 VibeVoice 的接入方案……

## [02:18]–[03:05]  说话人 1
那系统声音和麦克风要分开存吗？
```

**设计要点**：
- 写入用线程安全的同步追加（文件锁 / 串行 writer 线程）；`append_live` 在 ASR 工作线程中调用、无 event loop，故**不使用 aiofiles**（aiofiles 仅适用于纯 asyncio 场景）。
- live.md 中相邻同说话人段落合并，跨说话人不合并。
- final.md 调用一次完整 60min pass，说话人 ID 全局重编号（0,1,2...）。
- 说话人昵称映射：模型给出的是自动编号 `speaker_id`，UI 提供「重命名」把 `0 → 张三`、`1 → 李四`；该映射存入会议记录 JSON（`speaker_map`），并在 `final.md` / `summary.md` 回显。历史会议中亦可在会议详情里按段人工重指派说话人（见 §6.8）。

### 6.5 调度与编排（`meetvoice/orchestrator/`）

**职责**：串起捕获、录音、ASR、写入，管理滚动窗口与生命周期。

> **单一状态源约定（重要）**：`LiveSession` 是应用**唯一的状态源**。它内部维护状态枚举 `IDLE / RECORDING / PAUSED / PROCESSING / ERROR`，任何状态变更都通过 `on_state_change(state)` 回调广播；托盘图标、控制窗口、会议管理 UI **只订阅并渲染状态，不各自持有状态副本**。这样可避免"图标显示 recording 但 session 已卡死"这类双状态机不一致（见 §6.6 状态机）。

```python
# meetvoice/orchestrator/live.py（骨架）
import threading
from concurrent.futures import ThreadPoolExecutor
from loguru import logger as log
from meetvoice.summary import MeetingSummarizer   # §6.7 会后 LLM 会议总结
from meetvoice.meeting import MeetingStore         # §6.8 会议记录（单一事实来源）

class LiveSession:
    def __init__(self, cfg: Config):
        self.cfg = cfg
        self.capture = DualStreamCapture()
        self.recorder = WaveRecorder(cfg.recording_dir)
        self.asr = build_backend(cfg.asr)          # 四选一，默认 vibevoice_local
        # trash_dir 仅在 recycle 开启时传入，使级联删除走回收站（§6.8）；否则直接物理删除
        self.store = MeetingStore(
            cfg.recordings_dir,
            trash_dir=cfg.meetings.trash_dir if cfg.meetings.recycle else None,
        )
        self.window = RollingWindow(size_sec=cfg.window_sec,   # 默认 45s（最大上限）
                                    silence_sec=0.6)
        self.tasks = ThreadPoolExecutor(max_workers=1)  # 串行 ASR，防占满显存
        self._stop = False
        self._thread = None
        self.meeting = None
        self._on_done = None          # 终稿完成回调（见 stop_and_finalize / §6.6）

    def start(self):
        """后台线程启动采集+ASR，避免阻塞 UI 主线程。"""
        self.meeting = self.store.create()        # 创建会议记录 JSON（meeting_id=开始时间戳）
        self.writer = MarkdownWriter(cfg.notes_dir, meeting_id=self.meeting.id)
        self._thread = threading.Thread(target=self.run, daemon=True)
        self._thread.start()

    def pause(self):
        """暂停采集但保留缓冲与状态。"""
        self.capture.pause()

    def resume(self):
        self.capture.resume()

    def stop_and_finalize(self, on_done=None):
        """用户点击「停止」：结束采集并触发终稿；on_done 在终稿完成后回调（默认回到 idle）。"""
        self._stop = True
        self.capture._stop = True
        self._on_done = on_done

    def run(self):
        # 同步方法（在后台线程中跑），不使用 async/await
        self.recorder.open()
        self.writer.open_live()
        for sys_chunk, mic_chunk in self.capture.stream_chunks():
            self.recorder.feed(sys_chunk, mic_chunk)
            self.window.feed(sys_chunk + mic_chunk)   # 双路合并送 ASR
            if self.window.has_segment_ready():
                audio = self.window.drain()
                fut = self.tasks.submit(self._transcribe_and_write, audio)
                self._track(fut)                       # 异常回收
            if self._stop:
                break
        self._finalize()
        if self._on_done:
            self._on_done()   # 终稿完成后回调（如回到 idle），见 §6.6 TrayApp

    def _transcribe_and_write(self, audio):
        segs = self.asr.transcribe(audio, sr=24000, hotwords=self.cfg.hotwords)
        self.writer.append_live(segs)   # 同步、线程安全写入（见 §6.4）

    def _finalize(self):
        # 用完整录音跑一次终稿
        full = self.recorder.load_full_audio()
        segs = self.asr.transcribe(full, sr=24000, hotwords=self.cfg.hotwords)
        self.writer.write_final(segs)
        # 会后 LLM 会议总结（§6.7）；未启用或失败时降级，保留 final.md
        summary_path = None
        if self.cfg.llm.enabled:
            try:
                transcript = self.writer.format_plain(segs)   # 纯文本转写，去 Markdown 标记
                summary = MeetingSummarizer(self.cfg).summarize(transcript)
                summary_path = self.writer.write_summary(summary)
            except Exception as e:
                log.warning("会议总结失败，已保留转录稿：{}", e)
        # 回写会议记录（单一事实来源）：终稿/总结路径、说话人映射、状态
        self.store.mark_done(
            self.meeting,
            ended_at=now(), duration_sec=self.recorder.duration_sec,
            artifacts=self.writer.artifact_paths(summary_path),
            speaker_map=self.writer.speaker_map,
        )
```

**崩溃恢复（进程被强杀 / 断电兜底）**：
- `start()` 已 `MeetingStore.create()` 写入 `status="recording"` 的会议记录；**正常终稿后才会 `mark_done(status="done")`**。
- 应用启动时 `MeetingStore` 扫描到 `status` 仍为 `recording`（或 `failed`）且 `ended_at` 为空的记录，判定为「中断会议」，在「会议记录」列表置灰并标记"可恢复"。
- 用户点击「恢复」→ 复用已落盘的 `wav_sys/wav_mic` 重新跑 `_finalize`（终稿 + 总结），无需重新录音。这是 §1.2「可中断/可恢复」目标的落地。
- 仅在 `recorder.open()` 之前崩溃（连 wav 都没写）的记录，标记为 `failed` 并允许直接删除。

**窗口策略**：
- **按 VAD/句子边界切分，不硬切固定窗口**：`RollingWindow` 累积音频，当窗口内出现 ≥ `silence_sec`（默认 0.6s）的静音边界即 `drain()`，避免把一句话切在两半导致吞字/重复；`window_sec`（默认 45s）仅作**最大上限**，超过则强制切（防单段过长）。
- 串行提交 ASR（显存/内存敏感），队列积压超 3 段时丢最旧（已落盘录音兜底）。
- 终稿用完整录音一次性跑，发挥 60min 单 pass 的全局说话人一致性优势。

```python
# meetvoice/ui/app.py（骨架）
import pystray
from PySide6 import QtWidgets, QtGui, QtCore
from meetvoice.orchestrator import LiveSession
from meetvoice.config import Config

class TrayApp:
    def __init__(self, cfg: Config):
        self.cfg = cfg
        self.session: LiveSession | None = None
        self.icon = pystray.Icon("MeetVoice", self._load_icon("idle"),
                                 "MeetVoice", menu=self._build_menu())
        self.window = ControlWindow(cfg, self)  # QWidget，初始隐藏

    def _build_menu(self):
        return pystray.Menu(
            pystray.MenuItem("▶ 开始录音 + 识别", self.on_start),
            pystray.MenuItem("⏸ 暂停", self.on_pause, enabled=False),
            pystray.MenuItem("⏹ 停止并生成终稿", self.on_stop, enabled=False),
            pystray.Menu.SEPARATOR,
            pystray.MenuItem("📂 打开纪要目录",
                lambda: os.startfile(self.cfg.notes_dir)),
            pystray.MenuItem("📂 打开录音目录",
                lambda: os.startfile(self.cfg.recording_dir)),
            pystray.MenuItem("📋 会议记录…", self.show_meetings),  # 打开历史会议列表（§6.8）
            pystray.MenuItem("⚙ 设置…", self.window.show_settings),
            pystray.MenuItem("🪟 显示/隐藏控制窗口",
                self.window.toggle_visible),
            pystray.Menu.SEPARATOR,
            pystray.MenuItem("❌ 退出", self.on_quit),
        )

    def on_start(self):
        self.session = LiveSession(self.cfg)
        self.session.start()              # 后台线程跑音频采集+ASR
        self._set_state("recording")
        self.window.on_state_change("recording")

    def on_pause(self):
        self.session.pause()              # 停采集但不结束，保留缓冲
        self._set_state("paused")

    def on_stop(self):
        self._set_state("processing")
        # 终稿在后台线程生成；完成后经 LiveSession 回调回到 idle（单一状态源约定，见 §6.5）
        self.session.stop_and_finalize(on_done=self._on_finalized)

    def _on_finalized(self):
        self._set_state("idle")
        self.window.on_state_change("idle")

    def run(self):
        self.icon.run(detached=False)     # 阻塞主线程，托盘事件驱动
```

> **pystray + PySide6 集成要点（M5 实现时必须）**：两者的事件循环不能都占主线程。推荐做法——主线程创建 `QApplication` 并 `exec()` 驱动 Qt；`pystray.Icon` 用 `icon.run_detached=True`（或放到守护线程）在后台运行托盘；所有跨线程 UI 更新经 `QTimer`/信号槽回到主线程。注意 `ControlWindow` 必须在 `QApplication()` 之后创建，否则会触发 Qt 的 "no QApplication" 错误。上面 `TrayApp` 骨架为示意，M5 需补一段 `main()` 引导代码（见 §9.1 M5）。

**状态机**：

```
            start              stop+finalize
  idle ─────────────▶ recording ─────────────▶ processing ──▶ idle
   ▲                    │  ▲                       │
   │                    │  │                       │
   │       pause        │  │ resume                │
   └────────────────────┴  └──────────────────────┘
        (paused 状态，保留录音缓冲)
```

> **状态以 `LiveSession` 为唯一来源**：托盘/窗口只投影其状态，不另存副本（详见 §6.5 单一状态源约定），避免双状态机不一致。

**控制窗口与工作线程通信**：
- 工作线程（`LiveSession`）通过 `asyncio.Queue` 把新 segments 推给 UI 线程。
- UI 线程用 `QtCore.QTimer` 定时拉取并刷新预览文本（30fps 无必要，4Hz 足够）。
- 状态变更用 `threading.Event` + 回调，避免直接跨线程操作 Qt 控件（Qt 要求 GUI 操作在主线程）。

**模型管理 UI（下载 / 删除 / 启用）**：

由 `meetvoice/models/manager.py` + `meetvoice/ui/models.py` 支撑（模块设计见 [§8](#8-项目结构)）。设置页内嵌独立的「模型管理」面板，让用户**无需离开应用、无需手敲命令**即可获取与管理 ASR 模型。

- **模型目录（catalog）**：可下载模型清单由 `models_catalog.toml`（随包发布、可编辑）定义，每个条目含 `id / name / backend / model_path / target_dir / download(source+repo) / size_gb / languages / recommended`。`target_dir` 严格对应 §4.5.2 的存放目录（`models/vibevoice`、`models/funasr`、`models/vibeasr`），保证下载落点正确。

- **一键下载（落点正确）**：点「下载」→ `ModelManager.download(id)` 按 `download.source` 分发：
  - `hf` → `huggingface_hub.snapshot_download(repo, local_dir=target_dir)`；
  - `modelscope` → `modelscope.snapshot_download(repo, local_dir=target_dir)`；
  - `cli` → 子进程 `huggingface-cli download <repo> --local-dir <target_dir>`（GGUF，见 §11.1）。

  下载**直接落到 catalog 指定的 `target_dir`**（即 §4.5.2 规范目录），带进度回调与可取消；完成后自动刷新状态为「已下载」。离线/内网环境可事先手动放置，再用「刷新」识别。
- **删除**：点「删除」→ 经二次确认后物理移除该模型的 `target_dir`（仅删模型权重，不影响会议记录）；若删除的是当前启用模型，一并清空 `[models].active`。

- **自动启用规则（关键）**：启动时 `ModelManager.auto_enable()` 执行——若 `[models].active` 为空且**恰好只有一个**模型已下载，则自动将其设为启用（写入 active 与 `[asr]` 段），用户无需任何额外操作即可使用；若零个已下载则引导下载；若多个已下载且未指定，则**不猜测**、要求用户在面板中显式选择，避免意外切换后端。该行为受 `[models].auto_enable` 开关控制（默认开）。

**首次启动向导（Onboarding）**：
首次打开应用时，模型尚未下载、LLM key 可能未填。若直接进入录制主流程，极易因缺模型/缺配置而崩溃，劝退用户。故 M13 实现「首次启动向导」：

1. **硬件探测**：检测是否有可用 GPU（CUDA/MPS）；有则推荐 `vibevoice_local`（7B 高精度），无则推荐 `funasr_local`（CPU 中文兜底）。
2. **模型就绪引导**：若本地无模型权重，直接引导进入「模型管理」面板（见上文），按硬件推荐项点「下载」一键获取（下载严格落到 §4.5.2 目录）；离线/内网环境则用下方命令手动下载后，在面板点「刷新」即可识别为「已下载」。**不内置大文件分发**。若仅下载了一个模型，向导结束即自动启用（见自动启用规则），用户无需额外选择。
3. **可选 LLM 配置**：引导填写 `[llm]`（base_url / api_key / model）；**明确"跳过也能用"**——未配置时仅关闭会议总结，转录/纪要功能完整可用。
4. **输出目录确认**：确认 `recordings/` `notes/` 落盘位置（默认项目目录下，可改）。
5. 向导结束后写入 `config.toml`（含 `onboarded=true` 标记），再次启动跳过向导直接进入主界面；设置页可「重新运行向导」。

**系统通知（非阻塞）**：
关键事件通过 OS 原生通知（Windows Toast / macOS Notification）轻提示，不打断当前工作，与托盘状态联动：
- 会议自动停止并进入终稿处理 → "会议已结束，正在生成纪要…"

**配置优先级与热更新边界**：

**单实例与自启动**：

### 6.7 会议总结模块（`meetvoice/summary/`）

**职责**：会议停止、终稿 `final.md` 生成后，调用 OpenAI 兼容的大模型，把转写文本浓缩为结构化纪要。**仅会后调用一次，全程不上传任何音频**。

**为什么是 "OpenAI 兼容"**：连接参数全部可配置（见 §6.6 `[llm]`），用户可指向任意兼容服务——官方 OpenAI、`DeepSeek`、阿里云百炼，或本地 `Ollama` / `vLLM`（全本地、零外传）。**[llm].provider** 区分接入方式：`openai` 用配置的 `base_url`；`ollama` 则忽略 `base_url`、由 `ollama_host` 自动推导端点 `http://host:port/v1`，实现**本地大模型零配置接入**（UI 与 `meetvoice llm check/list/pull` 命令均围绕此设计）。客户端统一由 `meetvoice.llm.build_llm_client(cfg)` 按 provider 构造。

**产出 `summary.md`**，固定结构：

```
# 一句话摘要
…
# 详细摘要
…
# 关键决议
- …
# 待办事项（尽量标注负责人 / 截止时间）
- [ ] …
# 行动项
- …
# 未决问题
- …
```

> **防幻觉纪律**：模型只许依据 `final.md` 文本推理，未提及即标"未讨论"，不得补写转写里没有的内容（见上方 `SUMMARY_PROMPT` 第 1 条）。同时支持 `response_format="json_object"`（或 `json_schema`）的结构化输出模式，便于把行动项/负责人/截止时间直接同步进任务系统——`config.toml` 的 `[llm]` 可增 `structured=true` 开关，默认关（先出可读 md）。

**长会议处理（map-reduce）**：60min 转写可能超出模型上下文。按约 `max_tokens/2` 的 token 预算切片，逐块总结后再合并做二次总结；若仍超长则截断到模型上限，并在纪要注明"已截断"。

**骨架**：

```python
# meetvoice/summary/summarizer.py（骨架）
import os
from openai import OpenAI
from meetvoice.config import Config

SUMMARY_PROMPT = """你是一名严谨的会议记录助手。请仅依据下方转写稿输出结构化纪要，
严守以下纪律：
1. 不得编造转写稿中未出现的人名、数据、决议或行动项；某类信息未讨论时，写明"未讨论"。
2. 关键决议 / 行动项尽量引用原文时间戳（如 [14:32]），便于回查。
3. 输出包含：一句话摘要、详细摘要、关键决议、待办事项（务必标注负责人与截止时间）、
   行动项、未决问题。
转写稿如下：
{transcript}"""

class MeetingSummarizer:
    def __init__(self, cfg: Config, client=None):
        self.cfg = cfg.llm
        # client 可注入（测试用 fake）；否则按 provider 构造 OpenAI 兼容客户端
        from meetvoice.llm import build_llm_client
        self.client = client or build_llm_client(self.cfg)  # provider=ollama 时端点由 ollama_host 推导

    def summarize(self, transcript: str) -> str:
        prompt = (self.cfg.prompt_template or SUMMARY_PROMPT).replace(
            "{transcript}", transcript)
        resp = self.client.chat.completions.create(
            model=self.cfg.model,
            messages=[{"role": "user", "content": prompt}],
            temperature=self.cfg.temperature,
            max_tokens=self.cfg.max_tokens,
            timeout=self.cfg.timeout,
        )
        return resp.choices[0].message.content
```

**写入层配套**（`§6.4` `MarkdownWriter` 新增两方法）：
- `format_plain(segs)`：把 segments 转纯文本（去 Markdown 标记），作为 LLM 输入。
- `write_summary(text)`：落盘 `summary.md`，与 `final.md` 同目录。

**降级策略**：`llm.enabled=false` 或调用异常时，跳过总结、保留 `final.md`，仅记日志告警——**绝不因总结失败而丢失转录稿**。

### 6.8 会议管理模块（`meetvoice/meeting/`）

**职责**：把"一次录制 = 一个会议"作为一等公民，提供历史枚举、详情查看、回放与级联删除。所有信息以 §6.2 的会议记录 JSON 为单一事实来源。

**核心接口（骨架）**：

```python
# meetvoice/meeting/store.py（骨架）
from dataclasses import dataclass, field
from pathlib import Path
import json

@dataclass
class MeetingRecord:
    meeting_id: str
    started_at: str
    ended_at: str | None = None
    duration_sec: int = 0
    device: str = ""
    sample_rate: int = 24000
    hotwords: list[str] = field(default_factory=list)
    speaker_map: dict = field(default_factory=dict)   # {spk_id: 昵称}
    status: str = "recording"        # recording | done | failed
    artifacts: dict = field(default_factory=dict)   # wav_sys/wav_mic/live_md/final_md/summary_md/log

class MeetingStore:
    def __init__(self, recordings_dir: str, trash_dir: str | None = None):
        self.root = Path(recordings_dir)
        self.trash = Path(trash_dir) if trash_dir else None

    def create(self) -> MeetingRecord:
        """start() 时调用：生成 meeting_id=当前时间戳，写初始 JSON。"""
        mid = datetime.now().strftime("%Y%m%d_%H%M%S")
        rec = MeetingRecord(meeting_id=mid, started_at=iso_now())
        self._save(rec); return rec

    def mark_done(self, rec: MeetingRecord, **fields) -> None:
        """终稿完成后回写路径/状态。"""
        for k, v in fields.items(): setattr(rec, k, v)
        rec.status = "done"; self._save(rec)

    def list(self) -> list[MeetingRecord]:
        """枚举全部会议记录，按 started_at 倒序。"""
        return sorted((self._load(p) for p in self.root.glob("*.json")),
                      key=lambda r: r.started_at, reverse=True)

    def get(self, meeting_id: str) -> MeetingRecord | None: ...

    def delete(self, meeting_id: str) -> None:
        """级联删除：删除该会议 JSON 及其引用的全部产物文件。
        recycle=true 时先整体移入 trash/，否则直接物理删除。"""
        rec = self.get(meeting_id)
        targets = [self.root / rec.meeting_id + ".json",
                   *(self.root.parent / p for p in rec.artifacts.values())]
        if self.trash:   # trash_dir 已存在（[meetings].recycle=true）即走回收站
            self._move_to_trash(rec, targets)
        else:
            for t in targets: t.unlink(missing_ok=True)

    def export(self, meeting_id: str, dest_zip: str) -> Path:
        """单会议导出打包：将该会议全部产物（wav_sys/wav_mic/json/live.md/
        final.md/summary.md/log）打包为一个 zip，便于归档或外发。
        不含任何中间缓存，仅导出用户可见产物。"""
        rec = self.get(meeting_id)
        import shutil, zipfile
        zp = Path(dest_zip)
        with zipfile.ZipFile(zp, "w", zipfile.ZIP_DEFLATED) as z:
            z.write(self.root / (rec.meeting_id + ".json"),
                    arcname=rec.meeting_id + ".json")
            for p in rec.artifacts.values():
                src = self.root.parent / p
                if src.exists():
                    z.write(src, arcname=src.name)
        return zp
```

**回放与时间戳跳转**：`ui/meetings.py` 用 `python-vlc` / `PySide6.QMediaPlayer` 播放 `wav_sys`（或 sys+mic 混音）；`final.md` 的每行带 `[MM:SS]` 时间戳，点击该行 → 解析秒数 → `player.set_time(sec*1000)` 跳转。转写与音频因此可双向定位。

**说话人人工重指派**：详情页允许把某一段 `speaker_id` 改为另一已存在编号或新建昵称，重指派结果写入该会议记录的 `speaker_map` 并回显 `final.md` / `summary.md`（覆盖模型自动编号误差，弥补 §6.1 所述"同一麦克风多人坍缩"等情形）。

**测试**：`tests/test_meeting_store.py` 覆盖 `create → mark_done → list → delete → export` 全链路，并验证级联删除确实移除全部关联文件（及 recycle 模式移入 trash）、`export` 产物 zip 含全部可见文件。

**数据导出（单会议打包）**：会议详情页提供「导出」按钮，调用 `MeetingStore.export(meeting_id, dest)` 将该会议 wav/json/md/log 打包为一个 zip，便于归档或离线外发；导出不含任何中间缓存，仅用户可见产物。批量导出（多选会议）在 v2 考虑。

## 7. 关键技术决策

### 7.1 为什么不直接做流式 ASR

VibeVoice-ASR 的架构是"听完整段再产出结构化 JSON"，没有中间 token 流可吐（gradio demo 的 `TextIteratorStreamer` 流的是**最终 JSON 文本的逐字显示**，不是音频流式输入）。强行做亚秒级流式会丧失其 diarization 与长上下文优势。因此本方案把"实时"定义为**滚动 30–60 秒出稿**，而非逐字流式。

### 7.2 为什么默认 transformers 而非 vLLM

- transformers 直跑零服务化开销，单机使用更简单。
- vLLM 适合多并发场景（如同时转写多场会议），个人单机用不上。
- 若后续要做团队共享服务，再切 vLLM（OpenAI 兼容 API，客户端只改一个 URL）。

### 7.3 CPU 路径的定位（中文场景）

中文会议场景下，CPU 兜底**改用 FunASR / SenseVoice，不用 VibeASR.cpp**。理由：

| 模型 | AISHELL4 WER | AliMeeting WER | 中文定位 |
|---|---|---|---|
| VibeVoice-ASR-7B（GPU） | **19.83** | 36.21 | 最优，需 GPU |
| FunASR（Paraformer-large） | 20.41 | **39.27** | CPU 兜底首选，接近 7B |
| SenseVoice-Small | 22.52 | 38.75 | CPU 兜底备选，速度快 |
| VibeASR.cpp（BitNet） | 27.45 | 40.58 | **中文不推荐**，退化 7.6pp |

> 数据来源：VibeASR.cpp 官方 README benchmark 表（Microsoft 自评，可能有偏向，但相对排序与社区共识一致）。

- VibeASR.cpp 的 BitNet 量化用 1.5B LM 替换 7B，中文长会议退化尤甚（AISHELL4 WER 从 19.83 涨到 27.45，约 1/4 字错）。
- FunASR 是阿里达摩院中文专用模型，CPU 上 Paraformer-large 即可跑，原生支持热词、标点、时间戳、diarization（2026-05 起内置，亦可配 CAM++ 增强）。
- SenseVoice-Small 更轻、多语种，速度优于 FunASR，中文精度略低。
- 有 NVIDIA GPU（哪怕 T4/3060）时，VibeVoice-ASR-7B 路径体验与精度都明显更好，仍是默认。

### 7.4 实时字幕（可选路径 A）

> 本节省略概述；流式 ASR 的详细选型对比、双轨架构与"为何不全用流式"，见 [§7.7](#77-实时流式-asr-方案选型)。

若用户确实需要**逐字流式中文字幕**（亚秒级），方案扩展：预览通道改用 **FunASR `paraformer-streaming`**（中文优化，CPU 可亚秒出字，中文表现优于 faster-whisper），权威通道仍由 VibeVoice-ASR-7B 产出。预览不入库，仅显示。此为 v2 功能，v1 不实现。

```
音频流 ──┬──▶ VibeVoice-ASR-7B（滚动/终稿，权威，含 diarization）
        └──▶ FunASR paraformer-streaming（流式预览，低延迟，无 diarization）
                │
                ▼
         字幕悬浮窗/控制台
```

FunASR streaming 模型为中文优化，CPU 上可做到 0.3–0.5 秒出字，中文表现优于 faster-whisper。预览不入库，仅显示。

### 7.5 说话人分离质量

**这是"多说话人自动分离"需求的落地依据（v1.6 明确为产品目标）。**

- **两条主路径都原生自动分离，无需人工介入**：
  - VibeVoice-ASR-7B：联合 ASR+diarization+时间戳，60min 单 pass 内全局一致（论文数据：AMI-IHM DER 11.92，AISHELL-4 DER 6.77；微软官方页另称 DER 3.42%，论文另有引 AISHELL-4 DER 16.93%，评测条件/口径不同，实施前统一基准复核），**自动聚类说话人、无需指定人数**。
  - FunASR（CPU 兜底）：一次 `generate()` 即 VAD+ASR+标点+**原生 diarization**（2026-05 起内置，无需 CAM++），同样自动聚类。
- **滚动窗口模式编号不跨段一致**：第 N 段 `speaker_id=0` 与第 N+1 段 `speaker_id=0` 不保证同一人——这是终稿模式存在的核心理由。live.md 顶部显式提示"说话人编号仅段内有效，全局编号见 final.md"，final.md 经 60min 单 pass 全局重编号。
- **已知声学限制**：说话人分离依赖"每个说话人有独立声学特征"。若多人共用一支麦克风（本地 mic 物理混成一路），他们会被模型坍缩为同一说话人（见 §6.1）。远端参会者走系统声音（各自独立），本机多人建议各用独立麦克风（未来扩展）；v1 接受此上限，并允许在会议详情里**人工按段重指派说话人**弥补（§6.8）。
- **FunASR 兜底精度低于 VibeVoice-ASR**：CPU 场景 live.md 仅作"粗分说话人"，final.md 仍尽量用 GPU 跑 7B 终稿以获得更好一致性。

### 7.6 中文场景的模型选择决策树

```
有 NVIDIA GPU（≥ 8GB 显存）？
├─ 是 ──▶ 默认 VibeVoice-ASR-7B（transformers, bf16）   [WER 19.83]
│         或更小更开源的 MOSS-Transcribe-Diarize 0.9B    [CER 14.84，Apache-2.0]
│         显存不足时 device_map="auto" 分片，或切 vLLM
└─ 否 ──▶ 中文会议？
          ├─ 是 ──▶ FunASR Paraformer-large           [CPU 兜底，WER 20.41，已原生 diarization]
          │         速度优先可换 SenseVoice-Small
          └─ 否（纯英文）──▶ VibeASR.cpp BitNet        [英文 RTF<1，无 GPU]
```

**热词配置**（中文会议强烈建议）：
- VibeVoice-ASR 通过 `context_info` 传入人名/术语/公司名，每行一个。
- FunASR 通过 `hotword` 参数传入（UTF-8 字符串，空格分隔或列表）。
- 配置文件 `config.toml` 示例（与 §6.6 统一）：
  ```toml
  [asr]
  hotwords = ["张三", "李四", "VibeVoice", "飞书", "量子计算"]
  ```

### 7.7 实时流式 ASR 方案选型

用户问"有实时语音处理的方案吗"--有，但需区分"准实时滚动"（本方案默认，30–60s 出稿）与"真流式"（亚秒级字随音出）。VibeVoice-ASR 与 FunASR Paraformer-large 都是**批处理**模型，不是真流式。真流式需换模型族。

**本地流式 ASR 选项对比**（中文优先）：

| 方案 | 流式方式 | 中文质量 | diarization | CPU 可跑 | 延迟 |
|---|---|---|---|---|---|
| **FunASR online/streaming**（paraformer-zh-streaming） | chunk 流式（VAD 切片+增量解码） | 良（略低于离线 large） | 需配 CAM++，流式下精度降 | 是 | 0.5–1.5s |
| **SherpaONNX**（paraformer-streaming / zipformer） | 流式解码（支持 partial 结果） | 良 | 内置说话人识别可选 | 是 | 0.3–1s |
| **faster-whisper** chunked | VAD 切片+逐片转写 | 中（whisper-large-v3 中文尚可） | 无 | 是 | 1–3s |
| **whisper.cpp** stream example | 滑动窗口 | 中 | 无 | 是 | 1–3s |
| VibeVoice-ASR-7B | **非流式**（60min 单 pass） | 最优 | 原生 | 否（需 GPU） | 分钟级 |
| FunASR Paraformer-large（离线） | **非流式** | 优 | 需配 CAM++ | 是 | 10–60s 滚动 |

**推荐：双轨架构**（不牺牲终稿质量）：

```
音频流 ──┬──▶ 流式 ASR（FunASR streaming / SherpaONNX）  → 控制窗实时预览 + live.md（快）
        │       · 延迟 0.5–1.5s
        │       · 无 diarization 或粗分
        │       · 仅做"会议中可读"
        │
        └──▶ VibeVoice-ASR-7B（滚动 45s 窗口 + 会后终稿）  → final.md（权威）
                · 延迟 30–60s（滚动）/ 分钟级（终稿）
                · 原生 diarization + 时间戳 + 热词
                · 做会后可用纪要
```

**为什么不全用流式**：流式 ASR 为降延迟会缩减上下文窗口，导致：
- 说话人分离精度下降（全局一致性差）。
- 长句语义连贯性下降（句首被截断）。
- 热词收益降低（上下文不足）。
- 中文标点恢复质量下降。

所以流式只做"预览"，权威纪要仍由批处理模型产出。

**何时选哪个流式方案**：

| 场景 | 推荐 |
|---|---|
| 中文为主，要低延迟 | **FunASR paraformer-streaming**（中文专用，延迟 0.5–1.5s） |
| 多语种 / 要内置说话人识别 | **SherpaONNX**（多后端，灵活） |
| 已有 whisper 生态 | faster-whisper chunked（中文不如前两者） |
| 不需要真流式，准实时够用 | 直接用默认滚动窗口（FunASR-large 或 VibeVoice-7B），无需双轨 |

**实现位置**：新增 `meetvoice/asr/streaming_preview.py`，作为可选模块，仅当用户在设置里开启"实时预览"时启动，与主滚动/终稿通道并行。

> 注：流式模型的具体 model ID、API 参数（chunk 长度、partial 结果回调）需在 M10 阶段实测确认；FunASR 与 SherpaONNX 的流式 API 均有官方示例可参考（见 §11 参考资料）。

- [ ] **模型管理 UI**：设置页「模型管理」面板列出可选模型，支持一键下载到 §4.5.2 规范目录、删除已下载、启用（互斥）；仅下载一个时自动启用；离线可手动放置后「刷新」识别（§6.6）。

**v1 范围锁定（MVP 交付承诺）**：双路采集 + 多说话人自动分离 + 滚动出稿 + 会后终稿 + LLM 会议总结（可配置 OpenAI 兼容）+ 会议管理（历史查看/回放/级联删除）+ 模型管理 UI（M15）+ 托盘壳 + CPU 中文兜底（FunASR）。**明确不属 v1**：实时流式字幕（M10，v2）、云端同步与多人协作、跨设备。这些可在 v1 稳定后迭代。

### 9.3 评测基线（质量门禁）

方案前几版缺自有评测，后端选型依赖官方 benchmark。v1 收尾前建议建立**内部中文会议评测集**：

- 收集 5–10 段真实/脱敏中文会议录音（覆盖单人/多人、线上/线下、code-switch），人工标注参考转写与时间戳。
- 对 `final.md` 计算 **WER**（词错率）与 **DER**（说话人分离错误率，diarization error rate），对比 VibeVoice-ASR-7B、MOSS-Transcribe-Diarize、FunASR 兜底在**自有场景**下的真实差距。
- **新模型指标须本地复核**：MOSS / FireRedASR2S / Qwen3-ASR 的 CER/WER 数字来自联网调研的官方 benchmark（评测集与口径均非自有），**不得直接作为选型依据**；须纳入本评测集用相同口径重测（如 AISHELL-4 CER 须以自有中文会议集复算），避免"别人家的数"掩盖本地退化。
- 把评测脚本纳入 `tests/` 或 CI，作为后端/模型升级的回归门禁——避免"别人家的数"掩盖本地退化。
- 评测集本身不入仓库（含他人语音，隐私），存本地隔离目录，仅保留指标。

## 10. 风险与限制

| 风险 | 影响 | 缓解 |
|---|---|---|
| **VibeASR.cpp 中文精度差** | AISHELL4 WER 27.45，中文会议约 1/4 字错 | 中文场景**不用** VibeASR.cpp；CPU 兜底走 FunASR（WER 20.41）；VibeASR.cpp 仅保留英文场景 |
| **VibeASR.cpp 在 Windows 构建复杂** | M9 英文 CPU 路径在 Windows 可能卡在编译 | MSVC 不支持，必须装 MinGW-w64（WinLibs 一键包）；`setup_env.py` 不可用，走手动 `cmake -B build -G "MinGW Makefiles"`；M9 设为低优先可选 |
| 7B 模型显存占用 | 8GB 显存可能 OOM | transformers 路径支持 `device_map="auto"` 分片；vLLM 路径可 `--tp 2` 跨卡 |
| 滚动模式说话人跳号 | live.md 阅读体验差 | 顶部显著提示 + final.md 兜底；可选按音色简单聚类 |
| 长会议显存累积 | 60min 终稿可能爆显存 | 终稿走 vLLM（连续批处理）或分段合并 |
| 系统声与麦克风音量差异大 | ASR 漏字 | 双路独立归一化（峰值/能量归一），合并前各自限幅 |
| VibeVoice 仅限研究用途 | 不宜商用 | 定位个人/内部工具，README 注明 |
| Windows 采样率不匹配 | WASAPI 默认 48k，ASR 要 24k（FunASR/VibeVoice）或 16k（部分模型） | 捕获时实时重采样（`librosa.resample`），按后端期望采样率转换 |
| 隐私合规 | 录音含他人声音 | 默认本地不上传；会议前应告知参与者（合规建议） |
| 中文标点与断句 | FunASR 自带标点模型；VibeVoice-ASR 输出含标点 | 统一在写入层处理标点风格；可选关闭标点由后处理统一加 |
| **托盘与 Qt 事件循环冲突** | pystray 与 PySide6 各有事件循环，集成易卡死 | pystray 跑主线程（detached=False），Qt 窗口用 QTimer 驱动；或 pystray 用 `run_detached=True` + Qt 主循环；M5 实测选其一 |
| **关闭窗口误退出** | 用户点 ✕ 以为最小化，实际进程退出 | 默认拦截 closeEvent 转最小化到托盘；设置页可选"关闭即退出" |
| **双轨流式与终稿互斥** | 流式预览占用 CPU 与滚动 ASR 抢资源 | 流式用独立线程 + 独立模型实例；CPU 资源紧张时降级为仅滚动模式 |
| **录音设备被占** | 其他软件占用麦克风/扬声器导致 WASAPI 失败 | 启动时探测设备可用性；失败时托盘显红态并提示 |
| **LLM 总结依赖外部服务** | 断网 / 密钥失效 / 配额耗尽时 `summary.md` 生成失败 | `enabled=false` 或异常时降级，保留 `final.md` 并记告警；绝不因总结失败丢转录稿 |
| **总结隐私外传** | 转录含他人发言，发往外部 LLM 有泄露风险 | 默认由用户显式开启；可将 `base_url` 指向本地兼容服务（Ollama/vLLM）实现全本地零外传 |
| **长会议超上下文** | 60min 转写可能超出模型上下文窗口 | 分块 map-reduce 或截断到模型上限，纪要注明"已截断"；总结质量随截断下降 |
| **总结成本 / 延迟** | 每次会议一次 API 调用，长文本 token 费用与耗时 | 用轻量模型（gpt-4o-mini / 本地小模型）做总结；`enabled` 可关 |
| **同一麦克风多人无法区分** | 多人共用一支 mic 时，模型 diarization 将他们坍缩为同一说话人 | 声学限制，非 bug；远端走系统声（独立声源），本机多人建议各用独立麦克风；允许会议详情里人工按段重指派说话人（§6.8） |
| **会议删除误操作** | 级联删除会一次性清除该会议全部文件（含原始录音），误删难恢复 | 删除前二次确认；`[meetings].recycle=true`（默认）先移入 `trash/` 回收站，支持误删恢复；UI 明确提示"将删除全部关联文件" |
| **缺少自有评测** | 后端选型依赖官方 benchmark，本地真实场景可能退化而无感知 | 建内部中文会议评测集做 WER/DER 回归（§9.3），作为模型/后端升级门禁 |
| **说话人分离精度波动** | 嘈杂/重叠语音、远场拾音差时 DER 上升，final.md 说话人编号可能错乱 | 60min 单 pass 全局一致性优于滚动；允许人工重指派（§6.8）；必要时提示用户核对 |
| **崩溃恢复缺失** | 进程被强杀/断电时会议记录滞留 `recording` 状态，用户不知能否恢复 | M13 实现启动扫描+「中断会议」恢复入口（§6.5）；仅 `recorder.open()` 前崩溃的记为 `failed` 可删 |
| **系统通知权限/被静音** | OS 通知被系统/用户关闭，关键事件（终稿完成）用户无感 | 通知仅作辅助；主状态仍由托盘图标与会议记录列表呈现，不依赖通知必达 |
| **导出包隐私外传** | 导出 zip 含完整转写与录音，外发可能泄露与会者信息 | 导出前提示"含他人语音与转写"；建议脱敏或仅内部分发；评测集与归档同理（§10 隐私合规） |
| **配置热改未重启导致不生效** | 用户改了 backend/device 但未见效，误以为 bug | 明确热更新边界（§6.6），改动需重启项时 UI 显式提示"需重启" |

### 11.1 VibeASR.cpp 部署速查（已核验）

**Linux / macOS 一键安装**：

```bash
git clone --recursive https://github.com/microsoft/VibeASR.cpp.git
cd VibeASR.cpp
pip install -r requirements.txt
python setup_env.py
```

**Windows 手动构建**（MSVC 不支持，`setup_env.py` 不可用）：

```powershell
# 1. 先装 MinGW-w64（推荐 WinLibs），把 bin 加入 PATH
git clone --recursive https://github.com/microsoft/VibeASR.cpp.git
cd VibeASR.cpp

# 2. 用 MinGW 构建
cmake -B build -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release `
    -DCMAKE_C_COMPILER=gcc -DCMAKE_CXX_COMPILER=g++ `
    -DCMAKE_MAKE_PROGRAM=mingw32-make
cmake --build build --target asr_infer -j

# 3. 下载量化模型
pip install huggingface_hub
huggingface-cli download microsoft/VibeVoice-ASR-BitNet --local-dir models/vibeasr
```

**运行转写**：

```bash
./build/bin/asr_infer `
    --vae-model models/vibeasr/vibeasr-vae-encoder-i8_s.gguf `
    --lm-model  models/vibeasr/vibeasr-lm-i2_s-embed-q6_k.gguf `
    --audio input.wav -t 4
```

## 13. 未来演进方向：语音对话助手（Assistant Mode）

> 本节记录一个产品演进设想：**在现有"听（ASR）+ 想（LLM）"能力上，补一个"说（TTS）"，是否能成为一个大模型语音对话应用？** 结论是方向成立，但 TTS 只是最后 10%，前 90% 是对话范式的重构。仅作演进记录，不进入 v1/v2 范围（§1.3 非目标仍保留"不做 TTS"）。

### 13.1 可行性判断

现有系统已具备三条关键能力：

1. **音频采集**：双路 WASAPI loopback + 麦克风（§6.1）。
2. **ASR 语音转文字**：VibeVoice-ASR / FunASR（§6.3），且原生产出说话人与时间戳。
3. **LLM 文本对话**：OpenAI 兼容客户端，已封装 `MeetingSummarizer`（§6.7），`base_url` 可指向本地服务实现全本地。

若再补一个 **TTS 语音合成输出**，理论上就构成"听—想—说"闭环，可作为大模型语音对话应用。但需澄清：**"加个 TTS"只是最后一步**——当前架构是"会议转录器"，而语音对话助手是另一种交互范式，前面大量重构不在 TTS 本身。

### 13.2 与现有设计的关键差距

| # | 差距 | 现状 | 对话助手所需 |
|---|---|---|---|
| 1 | **采集范式** | 双路合并（系统声+麦克风）转录全场 | 仅麦克风识别"用户指令"，且必须**排除系统自身 TTS 回放声**（防自喂）；靠 VAD 端点检测判断用户说完 |
| 2 | **对话 vs 转录** | LLM 是 `summarize(transcript)` 一次性总结 | 多轮上下文管理（session/历史）、流式输出（首字 <1s）、可选工具调用；需新增 `ConversationSession` |
| 3 | **打断/唤醒（barge-in）** | 无 | 用户可在助手说话时插话，需 VAD+能量检测实现打断 |
| 4 | **实时性链路** | 会议转录容忍"会后终稿" | ASR <1s、LLM 流式首字 <1s、TTS 合成 <500ms 起步；当前"实时流式"在 v2（§7.4/§7.7），实时能力本未建 |
| 5 | **TTS 与录音隔离** | 双路含系统声 | 若 app 用 TTS 外放，其声音会被自身 loopback 采集形成回声；**对话模式须关闭 loopback，或 TTS 走独立输出通道不进录音** |

### 13.3 推荐定位

- **作为 v3 或独立的 "Assistant Mode"**，而非 v1/v2 功能堆叠。复用现有音频管线（采集/ASR）、LLM 客户端、配置体系（`[llm]` 段可直接复用），但交互状态机、UI、会话管理是另一套。
- **隐私友好**：若 ASR（FunASR/VibeVoice）+ LLM（本地 Ollama/vLLM）+ TTS（本地 CosyVoice / ChatTTS / Edge-TTS）全本地，则是一个**全本地语音助手**，与 MeetVoice 全本地理念一致。
- **与会议记录模式互斥/隔离**：录音时不开 TTS 外放（避免污染录音），对话模式不录系统声；两模式通过状态机切换，不并行。

### 13.4 双模式切换架构（Mode Switch）

用户确认：同一 App 应支持**会议助手模式**与**对话助手模式**两种形态，且**可切换**。据此明确双模式设计（演进阶段，v3 落地）：

- **会议助手模式（MeetVoice 现有形态）**：双路录音（系统声+麦克风）+ 转录 + 会后总结 + 会议管理，即本方案 v1/v2 全部范围。
- **对话助手模式（Assistant Mode）**：单路麦克风 + VAD 端点检测 + 多轮 LLM + TTS 语音输出；**不录系统声、不开 loopback**，避免采集自身 TTS 回放形成自喂。
- **共享基础设施**：音频采集层、ASR 适配器、LLM 客户端（`[llm]` 段）、配置体系（`config.toml`）、托盘外壳均为两模式共用；差异仅在「采集路由 + 交互状态机 + 是否启用 TTS」。
- **切换入口**：托盘菜单 / 启动选择器提供「会议助手 / 对话助手」模式开关；切换即重启对应工作流（互斥运行，不并行），当前会话状态清理后进入新模式。
- **互斥约束**：会议模式录音时不开 TTS 外放（防污染录音）；对话模式不启用系统声采集。两模式不可同时激活。
- **实现前瞻**：建议预留顶层 `AppMode` 枚举（`MEETING` / `ASSISTANT`）与应用引导（`AppBootstrap`），v1 仅实现 `MEETING`，但架构上不为将来切换埋坑。

### 13.5 不在当前范围

本需求仍聚焦会议记录。§1.3 非目标保留"不做 TTS 语音合成"。本节仅为演进记录，待 v1 稳定、评测基线（§9.3）建立后，再立项评估 Assistant Mode 的可行性与原型。
